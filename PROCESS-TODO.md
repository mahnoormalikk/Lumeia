# Process improvements (the workflow itself)

Improvements to the development workflow, noted as we learn them, so the system evolves deliberately rather than from memory. These are about how we work, not theme changes — theme changes go in CHANGELOG.md.

- [x] DONE (2026-06-18): Theme Check wired into the workflow — `shopify theme check` runs in /build before /review, is confirmed in /verify, and is CONVENTIONS rule 11. Reason it exists: the LLM theme-reviewer approved a `block.settings['x' | append: i]` filter-inside-`[]` that Shopify validation rejected on sync. Future hardening option: a git pre-push hook that runs theme check.
- [x] DONE (2026-06-18): Editor-freedom standard for custom sections/blocks defined in `.claude/SECTION-STANDARD.md` and made CONVENTIONS rule 12. Grounded in Pebble's real setting patterns (copy from blocks/text, grid, icon-box, group, image). First application: rebuild the payment/trust block to it.
- [x] DONE (2026-06-19): SECTION-STANDARD upgraded from "copy the patterns" to "reuse the snippets". Added a "Native Pebble snippets" section with paste-ready schema blocks + render calls + classes for padding (both idioms), typography, text colour, colour scheme, width, animation, icon size, taken verbatim from the theme's own files, plus the gotchas (one padding idiom only; `typography-style` does not emit `--color-gradient`; typography classes on the text element only; `motion-component` display; saved-instance id-rename reset). Principle 2 and the freedom map now point to it. Reason: a hand-rolled CSS-variable control is "improved Ali"; rendering `spacing-style` / `typography-style` / `size-style` / `motion-component` is native. First application: trust block taken to full Pebble parity (PR #58).
- [x] DONE (2026-06-19): Logged the "reused id with a tighter constraint" footgun in SECTION-STANDARD gotchas. The parity rebuild kept `secure_font_size`/`guarantee_font_size` ids but raised their `min` to 12; the Thrive saved instance still held `secure_font_size: 11`, which passed Theme Check (it does not validate instance values) but failed the GitHub→theme sync ("can't be less than 12") and rejected the whole template. It stayed dormant until a later template edit re-triggered validation. Lesson: Theme Check is not the sync's validator — read the sync log too; and tightening a constraint on a reused id requires cleaning existing saved instances.
- [x] DONE (2026-06-21): Logged the git-vs-open-editor conflict. A git push to a template and a live theme-editor session on that same template fight each other (the two-way GitHub sync race). The Why Lumeia git fix (PR #62) did not reflect for Stelios because he had the Collagen template open in the editor; he redid it manually, and his edit synced back to main. Rule going forward: settings and content tweaks Stelios can do himself → he does them in the editor (Claude supplies the exact values), no git push; structural / section-copy / code changes → Claude does them in git, but they are merged with the editor CLOSED on that template (already a known hazard — "never push a template you have open" — now bitten, so it is a hard coordination rule). Every template PR now carries a "merge with the editor closed" note.
- [x] DONE (2026-06-21): Rule — one PR is one merge. Pushing follow-up commits to an already-merged branch does nothing (they never reach main), which caused a real mix-up: list-item improvements pushed after PR #65 merged were invisible to Stelios. Any change after a merge = new branch off main + new PR. Check the PR is still open before pushing a follow-up. Added to /ship.
- [x] DONE (2026-06-25): Root cause of the recurring STALE REMOTE branches (finally diagnosed, not guessed). `delete_branch_on_merge` is already ON and works — but it only fires on an actual PR merge. The lingering remote branches came from ORPHAN commits pushed OUTSIDE a clean merge: a follow-up commit pushed to a branch whose PR had already merged RE-CREATES the remote ref with a commit no PR will ever merge, so auto-delete never touches it. Two real cases cleaned up today: `thrive-clone-product-section` (the flavour flash-fix commit pushed to it AFTER #82 merged — content later re-landed via #84) and `flavour-title-typography` (an old pre-squash #76 snapshot). This is the same "one PR = one merge" rule (line above) seen from the remote side: pushing to a merged branch doesn't just do nothing, it leaves an orphan branch. GUARD: (1) before pushing a follow-up to ANY existing branch, run `gh pr view <branch>` and confirm state=OPEN; if merged/closed, branch off main instead. (2) Sweep at /status (cold start) and /ship: list `git branch -r`, and delete any branch that is not a currently-open PR with `git push origin --delete <branch>` (after confirming its content is in main). The earlier "prune local branches" idea was only half the story — local pruning never touches the remote orphans; this is the remote-side fix.
- [x] DONE (2026-06-28): Documented the theme-reviewer environment fallback in PLAYBOOK ("Agents" section). Not a gap in the process itself — `/review` + `theme-reviewer` are correctly defined — but in some host environments the custom agent type is not registered as selectable, so it cannot be spawned by type. The fallback (run a `general-purpose` agent told to read and follow `.claude/agents/theme-reviewer.md` against `git diff main...HEAD`) gives the same independent fresh-context review; review is never skipped. Surfaced during the header-localization-v2/v3 work where this host could not spawn `theme-reviewer` by type.
