# Lumeia Theme Conventions

The rules every change follows. The builder follows them, the reviewer enforces them. This is the canonical list; PLAYBOOK.md summarises it. These apply to any page: landing pages, quiz funnels, PDPs, homepage.

| # | Rule | What good looks like | Why |
|---|---|---|---|
| 1 | Customer-facing text and images are schema settings, never hardcoded in liquid | A merchant can change every word and picture from the theme editor | so Translate and Adapt can carry it into Arabic; hardcoded text cannot be translated |
| 2 | Native first | use Pebble's own sections and blocks; build a custom section only when native genuinely cannot do it | keeps the editor familiar and theme updates clean |
| 3 | Never bulk-edit Pebble core files | extend through new files or added schema settings, not by rewriting their sections | a customised core file blocks future Pebble updates |
| 4 | CSS scoped to its section, never bare native-class selectors | target a section id or a section-specific class | a global rule silently overrides native settings across the whole store |
| 5 | Use brand tokens, never raw values | brand colour and font variables, not hex codes or font names typed inline | one change propagates; matches the brand everywhere |
| 6 | RTL and Arabic safe by construction | text lives in schema (translatable); layout works mirrored | bilingual store; Arabic is a hard requirement. Translation itself is Rashed, RTL polish is the developer |
| 7 | Shared change to both PDPs is applied to both templates; content that differs per product stays per product | structural tweaks land in product.complete-collagen.json (lead) and product.thrive-protein.json (mirror); shared section code is one file and hits both, only per-product content is duplicated. `product.json` is the legacy default, not a PDP | the two templates are separate files |
| 8 | Design references are reference-only | Figma, exported code, screenshots and reference URLs are a target to rebuild, never pasted in | exported or Figma code is not editable, not translatable, not native. Preferred path: read the Figma via the connector, then rebuild as a compliant section |
| 9 | Reuse, do not duplicate | reuse existing sections, snippets and CSS; one custom CSS file with tokens at the top | duplication is where drift and bloat start |
| 10 | Every change is verified | pulled back and checked; desktop visually by Claude, mobile by screenshot or the mobile script | a push success message is not proof |
| 11 | Every change passes Theme Check before review and ship | `shopify theme check` reports no errors (Liquid syntax, schema) on the changed files | the reviewer is an LLM and does not parse Liquid; a syntax error otherwise fails silently when the theme syncs |
| 12 | Custom sections/blocks meet the editor-freedom standard | the merchant can restyle and re-space it for desktop and mobile, not just edit text: typography, colour, width, padding, sizes, layout, per device, like a good Pebble section (see `.claude/SECTION-STANDARD.md`) | native-first gives this for free; a hand-rolled block that only lets you edit text is "improved Ali", not Pebble-grade |
| 13 | Grounded in testing and feasibility, never assumptions | a claim of "works" or "verified" rests on a test or hard evidence; anything that cannot be tested here (geolocation, an app's behaviour, payments and logistics, sometimes mobile) is flagged as untested and scheduled for a real test, never reported as done | assuming-it-works is how the geolocation and the v1 PDP assessment went out unverified |
| 14 | Third-party app CSS (Kaching etc.) never injects hardcoded customer-facing TEXT | style with scoped app classes and brand tokens; if a string must be added via CSS `content:`, localize it per locale (`html[lang="ar"] …::before { content: "…"; }`) and prefer a native app field for the text wherever the layout renders it; app-box CSS lives outside the repo, so mirror the final block into the build log | CSS `content:` text shows the same string in every language (Translate & Adapt and the app's own translator cannot see it); this is rule 1 applied to app CSS. Kaching's bundle header was first shipped hardcoded and had to be redone per locale |
| 15 | Catalogue SEO: accessory/gift and sample products are noindexed; hero products stay indexed | `snippets/lumeia-robots.liquid` emits `noindex,follow` on `/collections/all`, `/collections`, products of type `Accessory`, and products tagged `single-sachet`. A new accessory typed `Accessory` is covered automatically; the real PDPs (Complete Collagen, Thrive Protein) stay indexable | the gift/accessory products must stay published on the Online Store channel for Kaching (0 KWD line items) and Smooth (picks by order lines), so they can't be unpublished — noindex is how we keep them out of Google |

A change that breaks rule 1, 6, or 8, fails Theme Check (rule 11), or is reported done without being tested (rule 13), is a blocker, not a suggestion: these are the ones that quietly broke things before (the payment block was untranslatable and non-editable; a `block.settings['x' | append: i]` filter-inside-`[]` passed the LLM review and failed Shopify validation on sync).
